# Content-update guide

Lume specimen copy is owner-editable in a Google Sheet and synced into the repository before deploy. The app never fetches content at build time or runtime; generated TypeScript is committed and reviewed like any other source change.

## Where the content lives

| Concern | File | What it owns |
| --- | --- | --- |
| Specimen identity | `packages/data/src/specimen-identities.ts` | Stable `number`, `floor`, `plate`, `form`, `hue`, `qr`, and optional artwork. Do not edit these from the sheet. |
| Specimen catalogue assembly | `packages/data/src/specimens.ts` | Attaches generated copy to stable identity and exposes specimen lookup helpers. |
| Generated specimen copy | `packages/data/src/specimen-content.generated.ts` | Per-language specimen `name` and `notes`, generated by `bun run sync-content`. Do not hand-edit. |
| Localized UI strings | `packages/data/src/locales.ts` | The five locale bundles (`en`, `zh-tw`, `zh-cn`, `ja`, `ko`) keyed by `LocaleKey`. |
| Specimen glyph forms | `packages/data/src/glyphs.ts` | The 12 abstract SVG forms used by `specimen.form`. |
| Design tokens | `packages/data/src/tokens.ts` | Aurora gradients, accent palette, glass tiers. |

## Google Sheet format

Publish the owner-maintained sheet as CSV:

1. In Google Sheets, choose File -> Share -> Publish to web.
2. Pick the specimen worksheet.
3. Choose CSV and copy the published URL.

The CSV must have one row per existing specimen QR slug and these columns:

```csv
qr,name_en,notes_en,name_zh-tw,notes_zh-tw,name_zh-cn,notes_zh-cn,name_ja,notes_ja,name_ko,notes_ko
```

A short sample is committed at `docs/specimens.sample.csv`.

`qr` is a lookup key only. The sync validates it against the existing catalogue and writes generated copy keyed by the repository's known QR slugs. It never writes `number`, `floor`, `plate`, `form`, `hue`, or `image`, so sheet edits cannot mutate printed-signage identity.

## Syncing owner copy

Run the sync manually, then commit the generated diff:

```sh
LUME_CONTENT_CSV_URL="https://docs.google.com/spreadsheets/d/e/.../pub?output=csv" bun run sync-content
```

Equivalent explicit form:

```sh
bun run sync-content -- --url "https://docs.google.com/spreadsheets/d/e/.../pub?output=csv"
```

For local testing, pass a file path or file URL:

```sh
bun run sync-content -- --url docs/specimens.sample.csv --output /tmp/specimen-content.generated.ts
```

The command fails loudly when:

- a required column is missing;
- any `name_*` or `notes_*` cell is blank;
- a sheet row contains an unknown `qr`;
- an expected repository QR slug is missing from the sheet;
- the sheet contains duplicate rows for the same `qr`.

After a successful sync, review `packages/data/src/specimen-content.generated.ts` and commit it with the source change or content-update PR.

## Editing specimen identity

Identity still lives in `packages/data/src/specimen-identities.ts` and is intentionally not owner-editable from the sheet.

### Adding or removing a specimen

The catalogue is type-locked at 23 entries (`LUME_TOTAL_SPECIMENS`). Changing the count requires changes to:

1. `LUME_SPECIMEN_IDENTITIES` (add/remove the identity row).
2. `LUME_TOTAL_SPECIMENS` (the `as const` literal).
3. `LumeSpecimenNumber` (the union of allowed numbers).
4. The compile-time assertion `_AssertTwentyThree`.
5. The generated content CSV/source row for the new or removed QR slug.
6. The unit tests in `packages/data/src/specimens.test.ts`.

This is intentional friction — the visitor flow assumes 23 specimens across the gallery, progress chrome, completion reveal, and card.

### Reordering specimens within a floor

The visitor sees specimens in `number` order within each floor. To reorder:

1. Decide the new sequence.
2. Update each affected entry's `number` field.
3. Verify visitor order still spans `1..23` with no gaps.
4. Reprint QR signage if floor metadata is also part of the print layout.

## Editing the QR mapping

The `qr` field is the slug embedded in printed QR codes (`?c=<qr>`). It is the only identifier the scanner uses to look up a specimen.

> Reprint required. Changing a `qr` value invalidates the existing printed signage for that specimen. Always treat a QR-slug change as a deploy-and-reprint operation, not a content tweak.

Process:

1. Pick a new slug. Convention is `lu-NN-<short-name>`.
2. Update the relevant specimen's `qr` field.
3. Add/update the matching owner-sheet row and run `bun run sync-content`.
4. Regenerate printable QR codes from the dev QR page.
5. Replace printed signage alongside the deploy that ships the slug change.

## Editing locale UI strings

UI chrome, buttons, and recovery copy live in `packages/data/src/locales.ts`. The English bundle (`EN`) is the canonical key set; every other bundle must satisfy `LumeLocaleBundle`.

When adding a new key:

1. Add the key and English copy to `EN`.
2. Translate the key in `ZH_TW`, `ZH_CN`, `JA`, and `KO`.
3. Use the key via `useLocale().t.<key>` or `useLocale().format("<key>", vars)`.

Adding a new language is a structural change touching `LUME_LOCALES`, `LumeLocale`, labels, generated content columns, and every locale consumer. Open an issue before starting.

## Smoke checks before committing

Run the standard quality gates after any content change:

```sh
bun run sync-content -- --url <published-csv-url>
bun test
bun run check
bun run typecheck
```

The tests and sync validation catch missing translations, duplicate QR slugs, gaps in `number`, unknown sheet rows, and missing generated content.

## Common pitfalls

- Forgot to commit generated content. Builds remain deterministic only when `packages/data/src/specimen-content.generated.ts` is in the PR.
- Changed `qr` in the sheet. The sync fails instead of mutating printed-signage identity; update `packages/data/src/specimens.ts` only when you really intend a signage change.
- Copy is too long for the gallery tile. Shorten localized names rather than widening layout in a content PR.
- Edited only English. The sync requires all five locale cells, but it cannot detect stale translations whose meaning no longer matches.
